cPGuard 事件分析：保護伺服器的資安工具，更新通道被劫持 70 分鐘

攻擊者入侵 OPSSHIELD 帳務與授權伺服器並竊取更新金鑰，經 cPGuard 官方更新通道推送假更新約 70 分鐘，約 2,950 台客戶伺服器被以 root 權限讀走機密並留下隱藏的 root shell。

分析日期：2026-11-09分類：供應鏈安全原始來源：OPSSHIELD標籤：cPGuard供應鏈攻擊更新通道Linux 伺服器憑證外洩OPSSHIELD

1. 概述

cPGuard 是 OPSSHIELD 開發的 Linux 網站伺服器安全套件（惡意程式掃描、防火牆與攻擊防護），多用於 cPanel 等主機代管環境。2026 年 11 月 1 日至 2 日，一名攻擊者先註冊成為 OPSSHIELD 的顧客，再入侵其帳務與授權伺服器，竊取發布更新所用的金鑰，於 11 月 2 日凌晨（UTC）經 cPGuard 官方更新通道推送假更新，窗口約 70 分鐘。約 2,950 台在窗口期內上線並執行假更新的客戶伺服器，被以 root 權限讀走密碼雜湊、root SSH 私鑰、MySQL root 密碼與 shell 操作歷史，並被留下一個隱藏的 root shell。OPSSHIELD 於 11 月 3 日發布完整的事件披露，含逐時時間線、入侵指標（IoC）與客戶處置步驟。本篇依其官方披露撰寫，BleepingComputer 的報導（含廠商發言人說法）為佐證。

3. 技術分析

3.1 入侵路徑：從顧客帳號打進帳務系統

攻擊者不是從外部硬闖，而是先成為「顧客」：註冊帳號、啟用試用，並在自己的伺服器上安裝正版 agent，藉此研究 agent 如何與授權系統互動。其間 cPGuard 曾兩度封鎖攻擊者，但攻擊者最後經帳務入口的 callback 頁面送出特製請求，取得帳務與授權伺服器的指令執行權限，再從該伺服器竊取發布更新用的存取金鑰。OPSSHIELD 明說，其日誌沒有記錄下造成突破的那一則確切請求；廠商已修補找到的兩個可能入口，並正逐行複查相關供應商元件，同時已排除 SSH、控制面板、FTP 與 API token 等路徑。也就是說，確切的初始漏洞截至披露時仍未定版，本篇不臆測其類型。

3.2 假更新的行為：70 分鐘窗口、一次性的資料蒐集

假更新是版本序號 5.88.12 至 5.88.19 的惡意腳本（四個變體，檔名樣式 cpguard-v58812-i91511*.sh）。它不是長期植入程式，而是一次性蒐集腳本：以 root 權限讀取 /etc/shadow 與 /etc/passwd（本機密碼雜湊）、/root/.ssh（root SSH 私鑰、authorized_keys、known_hosts）、/root/.my.cnf（MySQL root 密碼，如存在）、root 的 shell 操作歷史（常含手打的密碼與 token），少數伺服器還包括 /root/.s3cfg 的雲端儲存金鑰，然後回傳至攻擊者控制的端點（IoC 中列有 *_rx.php 接收端點）。此外它留下兩件東西：setuid-root 的隱藏 shell /var/tmp/.cpg91511_sh，以及排程任務 /etc/cron.d/i93677 與目錄 /var/tmp/.i93677/。只有在 02:08–03:20 UTC 窗口內上線並裝到假更新的伺服器才受影響；OPSSHIELD 的判斷標準是：窗口內有上線者，應假定其 root 等級機密已被攻擊者掌握。

3.3 廠商端的植入更深一層

OPSSHIELD 公布的 IoC 後三列——gsocket 後門（/usr/bin/defunct 等）與 Go 植入程式副本（/usr/sbin/pythno3 等）——廠商明說來自其自家內部伺服器，不是客戶伺服器。這表示攻擊者在廠商端的據點比客戶端的一次性腳本更完整，且植入會躲避 ps、netstat、ls、find 等標準工具的檢視，廠商建議從可信的開機環境或已知良好的靜態二進位檔檢查。客戶伺服器端目前公開的殘留物只有上述 root shell 與排程任務，兩者不可混為一談。

3.4 影響範圍

  • 執行假更新的客戶伺服器：約 2,950 台（廠商發言人對 BleepingComputer 的說法為 2,946 台），暴露內容為密碼雜湊、root SSH 金鑰、MySQL root 密碼與 shell 歷史。
  • 帳務入口帳號：約 7,900 筆，含姓名、公司、郵寄地址、電子郵件與雜湊後的密碼（bcrypt）；廠商要求全體用戶預防性重設帳務入口密碼。
  • OPSSHIELD 自身：帳務與授權等伺服器被入侵、三台雲端伺服器遭複製，廠商已從乾淨映像重建。

4. 歸因與證據限制

  • 本事件的核心事實目前以 OPSSHIELD 的單方披露為據；其時間線與 IoC 完整且具體，BleepingComputer 的報導取得廠商發言人說法，數字（2,946 台、帳務資料庫遭複製）與披露一致，但尚無第三方鑑識報告公開驗證。
  • 攻擊者身分不明，OPSSHIELD 未做任何歸因，本篇亦不歸因。攻擊者操作 IP 94.183.188.91 為廠商公布的 IoC，僅供比對，不代表身分。
  • 初始入侵的確切手法未定版：廠商自承日誌未錄得突破請求、已修補兩個「可能」入口。任何把入口寫成特定漏洞類型的說法都超出目前證據。
  • 影響數字在事件初期曾有較小的先行估計（媒體報導廠商曾提及攻擊者取回的檔案數），最終以廠商 11 月 3 日擴大披露的約 2,950 台為準；早期數字是「取回檔案」的初步估計，不是受影響伺服器總數，引用時不可混淆。
  • OPSSHIELD 在披露結尾提到「攻擊者如今使用 AI 工具」是其對攻擊速度的一般評論，並非本案攻擊者使用 AI 的證據，本篇不將本案定性為 AI 攻擊。

5. 防守建議

給 cPGuard 使用者（依廠商處置清單）：

  • 更新至最新乾淨版本（擴大披露指向 v5.88.26；最初警示為 5.88.25 或更新），並確認 /etc/cron.d/i93677、/var/tmp/.i93677/ 與 /var/tmp/.cpg91511_sh 已不存在。
  • 全面輪替：root 與所有本機使用者密碼、root SSH 金鑰（並從所有信任它的伺服器移除舊金鑰、複查 authorized_keys）、MySQL root 與 /root/.my.cnf 內的資料庫密碼、root shell 歷史中出現過的任何密碼、API 金鑰與 token、/root/.s3cfg 的雲端金鑰。
  • 檢查能用這些 SSH 金鑰連入的其他伺服器，在金鑰更換前視同已暴露。
  • 重設 OPSSHIELD 帳務入口密碼並開啟雙因素登入。
  • 若廠商通知攻擊者曾手動登入你的伺服器，從 11 月 1 日之前的乾淨備份重建。

給所有使用自動更新軟體的人（本案的通則教訓）：

  • 「更新通道」本身就是最高權限的供應鏈：任何以 root／系統權限自動更新的 agent，其發布金鑰與發布流程就是整批客戶的命門。選用這類工具時，應把廠商的金鑰管理與事件透明度列入評估。
  • 更新來源憑證與一般業務系統憑證應分離、分權限、分生命週期；本案攻擊者是從帳務系統橫向拿到更新金鑰。
  • 對安全工具本身也要做資產與版本盤點：出事時要能立刻回答「哪些主機在窗口期裝了哪個版本」。
